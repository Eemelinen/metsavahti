# 01 — Technical Description (under the hood)

## 1. System overview

Metsävahti is a monolithic Next.js 15 application with Payload CMS v3 embedded (same process, same Postgres). It has four concerns:

1. **Ingestion** — fetch forest-use declarations (metsänkäyttöilmoitukset) from the Metsäkeskus open-data WFS for the bounding boxes of active watch areas, normalise them, and upsert them into the local `declarations` table.
2. **Matching** — spatially intersect declarations with watch-area buffer polygons (PostGIS) and detect what is _new_ or _changed_ relative to what each watch area has already seen.
3. **Notification** — turn matches into `alerts`, group them per user according to their digest preference, render emails, send them, and log delivery.
4. **Product** — auth, watch-area management, dashboard, alert feed, account/GDPR self-service, legal pages.

```
Metsäkeskus WFS ──(2×/day cron)──> fetch-declarations ──> declarations table (PostGIS)
                                                                │
                                   match-watch-areas <──────────┘  ⋈ watch_areas.geom_3067
                                                                │
                                          alerts table <────────┘
                                                                │
                                      send-notifications ───────┘──> Resend / Mailpit ──> notification_log
```

## 2. External data source

- Endpoint: `https://avoin.metsakeskus.fi/rajapinnat/v1/ows/` (WFS 2.0.0; also WMS). Base URL is `WFS_BASE_URL` env so tests can redirect it.
- Layer name and attribute list must be discovered at bootstrap with `GetCapabilities` + `DescribeFeatureType` and pinned in `src/lib/wfs/layer.ts` (ticket MV-021). The data model is being renewed by Metsäkeskus; the client is an adapter behind `WfsClient` interface so a new layer version is a new adapter, not a rewrite.
- CRS: EPSG:3067 (ETRS-TM35FIN). Request `srsName=EPSG:3067`, `outputFormat=application/json` (GeoJSON). Fall back to GML via `fast-xml-parser` only if JSON is refused.
- Query strategy: one `GetFeature` per **cluster of watch areas** — watch areas are grouped into 3067 bboxes (max e.g. 20×20 km, padded by max radius); each bbox is one request with `BBOX=minx,miny,maxx,maxy,EPSG:3067`, paged with `count`/`startIndex` (page size 1000). Never download whole municipalities in the job path.
- Update cadence: Metsäkeskus updates 09:00 and 21:00 Finnish time. Cron runs 09:30 and 21:30 Europe/Helsinki.
- Licence CC BY 4.0: attribution stored as a constant and rendered in footer and emails.
- Semantics to surface in UI: a declaration is an _intention_ (no obligation to cut), must be filed ≥10 days before cutting, valid 3 years. Small household cuts and <13 cm mean-diameter stands are exempt (i.e. the service cannot see everything).

## 3. Data model

Payload collections (Postgres tables generated by Payload) plus PostGIS columns added via Drizzle migrations that Payload does not manage.

### 3.1 `users` (Payload auth collection)

- `email` (unique), `password` (hashed by Payload), `name?`, `locale` (`fi`|`en`, default `fi`), `timezone` (default `Europe/Helsinki`)
- `emailVerified` (Payload `verify: true`), `marketingConsent: boolean`, `marketingConsentAt?`
- `notificationPrefs`: `{ enabled: boolean, mode: 'immediate'|'daily'|'weekly', dailyHour: 9 }`
- `plan`: `'free'` (limit constants in `src/config/plans.ts`, free = 2 watch areas)
- `deletedAt?` (soft-delete marker used only during the deletion job; row is hard-deleted at the end)
- Access: users read/update self only; admins all.

### 3.2 `watch_areas`

- `owner` → users, `name`, `centerLng`, `centerLat` (WGS84 stored by Payload point field `center`), `radiusM` (int, 100–5000), `notificationsEnabled` (bool), `addressLabel?` (geocoded string), `lastCheckedAt?`, `lastDeclarationCount?`
- PostGIS (migration): `geom_3067 geometry(Polygon,3067)` maintained by a **trigger** on insert/update: `ST_Buffer(ST_Transform(ST_SetSRID(ST_MakePoint(centerLng, centerLat),4326),3067), radiusM, 'quad_segs=16')`; GIST index.
- Access: owner only.

### 3.3 `declarations` (cache of WFS features; not user-editable, admin read-only)

- `sourceId` (Metsäkeskus feature id, unique), `sourceLayerVersion` (string), `cuttingTypeCode`, `cuttingTypeLabel` (derived via `src/lib/wfs/codes.ts`), `areaHa` (numeric), `receivedAt` (date declaration received), `validUntil` (receivedAt + 3 years), `municipalityCode?`, `rawAttributes` (jsonb, the full validated attribute object), `geomHash` (sha256 of canonical WKB), `attrHash` (sha256 of sorted attribute JSON), `firstSeenAt`, `lastSeenAt`, `removedAt?` (set when a previously seen feature stops appearing in results for its bbox 3 consecutive runs)
- PostGIS: `geom geometry(MultiPolygon,3067)`, GIST index; `centroid geometry(Point,3067)`.
- Upsert semantics: on conflict `sourceId` update `lastSeenAt`; if `geomHash` or `attrHash` differ → update row, keep old hashes in `declaration_revisions` (id, declarationId, prevGeomHash, prevAttrHash, prevRawAttributes, changedAt).

### 3.4 `watch_area_declarations` (join / "seen" state)

- `watchArea` → watch_areas, `declaration` → declarations, `firstMatchedAt`, `lastMatchedAt`, `lastSeenGeomHash`, `lastSeenAttrHash`, `distanceM` (ST_Distance centre→polygon, 0 if inside), unique (watchArea, declaration).
- This table is what makes the pipeline idempotent: an alert is only created when a row is _inserted_ or its stored hashes differ from the declaration's current hashes.

### 3.5 `alerts`

- `user` → users, `watchArea` → watch_areas, `declaration` → declarations, `changeType` (`new`|`geometry_changed`|`attributes_changed`|`removed`), `createdAt`, `readAt?`, `notifiedAt?`, `snapshot` (jsonb: cuttingTypeLabel, areaHa, distanceM, receivedAt at time of alert — so the feed is stable even if the declaration changes later)
- Access: owner read + mark read; no create/update from client.

### 3.6 `notification_log`

- `user`, `type` (`alert_immediate`|`alert_digest`|`verify_email`|`password_reset`|`email_change`|`data_export`|`account_deleted`), `alertIds[]`, `provider`, `providerMessageId?`, `status` (`queued`|`sent`|`failed`), `error?`, `sentAt`.

### 3.7 `consent_events`

- `user`, `kind` (`terms`|`privacy`|`marketing`|`cookies`), `version` (string, e.g. `privacy-2026-09`), `granted` (bool), `ip?` (truncated to /24), `userAgent?`, `createdAt`. Append-only; used for the consent-history UI and audit.

### 3.8 `data_export_requests`

- `user`, `status` (`pending`|`ready`|`expired`|`failed`), `fileKey?` (object storage key or Payload upload id), `expiresAt`, `createdAt`.

### 3.9 `job_runs`

- `task` (`fetch-declarations`|`match-watch-areas`|`send-notifications`|`cleanup`|`export`|`delete-account`), `startedAt`, `finishedAt?`, `status`, `stats` (jsonb: requests, features, upserts, matches, alerts, emails), `error?`. Surfaced in Payload admin and `/api/health`.

### 3.10 Legal documents (`legal_documents`, Payload globals or collection)

- `slug` (`privacy`|`terms`|`cookies`|`accessibility`), `version`, `publishedAt`, `body` (rich text), `changeSummary`. Pages render the latest published version; `consent_events.version` references these.

## 4. Pipeline (Payload Jobs)

All tasks are registered in `src/payload/jobs/`. The queue is Postgres-backed. A single entrypoint `POST /api/jobs/run` (Bearer `CRON_SECRET`) enqueues `pipeline` which runs the three steps sequentially and records a `job_runs` row per step. `pnpm jobs:run` runs the same locally.

### 4.1 `fetch-declarations`

1. Load active watch areas (owner not deleted, notifications don't matter here).
2. Compute padded 3067 bboxes, cluster with a simple grid (cell 20 km) to minimise requests.
3. For each bbox: paged `GetFeature`; each page parsed → Zod schema `WfsFeatureSchema` → `NormalisedDeclaration` (`src/lib/wfs/normalise.ts`).
4. Bulk upsert into `declarations` in transactions of 500; compute hashes in app code; write revisions on change.
5. Track which `sourceId`s were seen per bbox; features previously present in that bbox but missing now get `missingRuns += 1`; at 3 → `removedAt = now`.
6. Errors: per-bbox failures are logged and retried 3× with backoff; a failing bbox does not abort others. Job status `partial` if any bbox failed.

### 4.2 `match-watch-areas`

Single SQL statement (in `spatial-queries.ts`):

```sql
INSERT INTO watch_area_declarations (...)
SELECT w.id, d.id, now(), now(), d.geom_hash, d.attr_hash,
       ST_Distance(ST_Transform(w.center_point_4326,3067), d.geom)
FROM watch_areas w
JOIN declarations d ON ST_Intersects(w.geom_3067, d.geom)
WHERE d.removed_at IS NULL AND d.valid_until > now()
ON CONFLICT (watch_area_id, declaration_id) DO UPDATE SET last_matched_at = now()
RETURNING ..., (xmax = 0) AS inserted;
```

- Rows where `inserted` → alert `new`.
- Existing rows where stored hashes ≠ declaration hashes → alert `geometry_changed`/`attributes_changed`, then update stored hashes.
- Declarations with `removedAt` set since last run and a join row → alert `removed` (optional, feature-flagged `ALERT_ON_REMOVED`).
- Update `watch_areas.lastCheckedAt`, `lastDeclarationCount`.

### 4.3 `send-notifications`

- Select alerts with `notifiedAt IS NULL` grouped by user.
- Respect `user.notificationPrefs` and `watchArea.notificationsEnabled`:
  - `immediate`: one email per watch area per run (may contain several alerts).
  - `daily`/`weekly`: skip unless the run is the scheduled digest run (09:30 daily; Monday 09:30 weekly); then one digest email with all pending alerts.
- Render with React Email (`src/emails/`), send via `payload.sendEmail`, write `notification_log`, set `alerts.notifiedAt`. Failures stay un-notified and retry next run; after 5 failures log `failed` and stop retrying that alert.
- Email contains: watch area name, per-alert rows (cutting type label, area ha, distance, received date), CTA link to `/ilmoitukset/[id]`, static map image URL (`/api/map-image/[alertId].png` rendered server-side with a simple SVG → PNG via `@resvg/resvg-js`; can be phase 2 — email must degrade gracefully without it), unsubscribe link (signed token → disables notifications for that watch area without login), attribution.

### 4.4 `cleanup` (weekly)

- Delete `declarations` with `validUntil < now() - 30d` and no alerts referencing them in the last 90 days; delete `declaration_revisions` older than 1 year; expire `data_export_requests`; purge `job_runs` older than 90 days.

### 4.5 `export` (per request)

- Builds a zip: `account.json`, `watch-areas.geojson` (WGS84), `alerts.json`, `consents.json`, `notifications.json`. Stored via Payload upload collection `exports` (private, `access: owner`), 24 h expiry; sends email with signed download link.

### 4.6 `delete-account`

- Verifies password already checked at request time; deletes in order: alerts, watch_area_declarations, watch_areas, notification_log (keep anonymised counts in an aggregate table if analytics needed), consent_events (keep with `user = null` and hashed email for legal proof of consent withdrawal? → decision: keep `consent_events` with user nulled and email replaced by sha256), data exports, sessions, user row. Sends "account deleted" email to the address _before_ deletion. Logged in `job_runs`.

## 5. Geo module (`src/lib/geo`)

- `crs.ts`: registers `EPSG:3067` in proj4; `toWgs84(x,y)`, `to3067(lng,lat)`.
- `buffer.ts`: pure TS helpers for previews on the client (turf `buffer` on WGS84 is fine for preview; authoritative geometry is PostGIS).
- `bbox.ts`: `bboxFor(watchAreas, paddingM)`, `clusterBboxes(bboxes, cellSizeM)`.
- `hash.ts`: canonical WKB (from GeoJSON via `wkx`) → sha256; attribute hash from stable-stringified object.
- `spatial-queries.ts`: all SQL touching geometry columns (Drizzle `sql` tags). Nothing else may write raw SQL.

## 7. Auth & sessions

- Payload local auth strategy with HTTP-only cookie, `verify: true`, `forgotPassword` enabled, `maxLoginAttempts: 5`, `lockTime: 10 min`.
- Email change: new address stored in `pendingEmail` + token; applied on confirmation; both addresses get a notice.
- Sessions list: Payload v3 sessions (`useSessions`) exposed on `/tili/turvallisuus` with revoke-others.
- Middleware `src/middleware.ts`: redirects unauthenticated `/vahtialueet/*`, `/ilmoitukset/*`, `/tili/*` to `/kirjaudu?next=`; unverified users to `/vahvista-sahkoposti`.

## 8. Consent & cookies (GDPR)

- Cookie categories: `necessary` (session, CSRF, consent cookie), `analytics` (optional; Plausible/Umami loaded only after consent). No marketing category in v1.
- Consent stored in cookie `mv_consent` (JSON, 12-month expiry) and, for logged-in users, in `consent_events`.
- Registration writes `terms` and `privacy` consent events with the current `legal_documents.version`; if a legal doc version changes, the app shows a re-acceptance banner (`/tili` and dashboard) — soft prompt, not a block, unless `requiresReacceptance` is set on the document.
- Retention rules encoded in `cleanup` and documented in the privacy page from the same constants (`src/config/retention.ts`) so policy and code cannot drift.
- Data subject rights implemented in-app: access/portability (export), rectification (profile edit), erasure (delete account), restriction/objection (notification toggles + marketing consent), withdrawal (same toggles). Public `/tietopyynto` form emails the DPO address for non-users.

## 9. Security

- All inputs Zod-validated; Payload access control per collection; Server Actions check ownership again (never trust ids).
- Rate limiting on auth routes, geocode, preview, contact and data-request forms.
- Signed tokens (unsubscribe, export download, map image) via `jose` HS256 with `TOKEN_SECRET`, short expiry, single purpose claim.
- CSP with nonce; map tiles/WMS domains allow-listed. HSTS. `SameSite=Lax` cookies.
- Secrets validated at boot by `src/env.ts`. Admin UI at `/admin` protected by Payload admin role; block indexing.
- Dependency audit in CI (`pnpm audit --prod` non-blocking, Dependabot weekly).

## 10. Observability

- pino logger with `runId`, `task`, `userId` (hashed) fields. Sentry for exceptions in server, jobs and client.
- `/api/health` returns `{ db: ok, lastPipelineRun: {...}, wfsReachable?: (only when ?deep=1) }`; uptime monitor hits it.
- Payload admin shows `job_runs` for manual inspection; a "Run pipeline now" admin action (admin only).

## 11. Configuration constants (`src/config/`)

- `plans.ts` (limits), `retention.ts`, `notifications.ts` (digest hours), `wfs.ts` (page size, cluster size, padding, timeouts), `cutting-types.ts` (code → fi label, colour token, severity).

## 12. Environments

- `development`: docker PostGIS + Mailpit, WFS → real endpoint by default (or mock via `WFS_BASE_URL=http://localhost:4010`).
- `test`: Testcontainers DB, WFS mock, Mailpit/NOOP email.
- `preview` (Vercel): separate DB branch, real WFS, Resend sandbox domain.
- `production`: managed PostGIS, Resend, cron enabled. Feature flags via env (`ALERT_ON_REMOVED`, `ENABLE_MAP_IMAGES`, `ENABLE_ANALYTICS`).

## 13. Non-functional targets

- Pipeline run for 1 000 watch areas ≤ 10 min, ≤ 200 WFS requests.
- P95 dashboard TTFB < 500 ms (declarations served from local cache, never live WFS on page load).
- Zero duplicate alerts across re-runs (integration test enforces).
- WCAG 2.1 AA on all public and app pages (axe in E2E).
